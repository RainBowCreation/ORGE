# Engine Track (DESIGN.md §2) — Native Conduction Step via JNI

**Date:** 2026-05-29
**Status:** Approved design; implementation plan to follow.
**Branch:** `rebuild`. Submodule: `ORGE-ENGINE` (C++ engine, edited additively).

## Goal

Replace the no-op `StubEngine` with a real `OrgeEngine` backed by the C++ ORGE-ENGINE
conduction kernel, called **in-process** from `:core`. The mod gets actual heat
conduction; this is the producer that makes the §5 section store non-inert and the gate
for any visible in-game thermal behavior (§7 phase change later).

Scope is the **engine seam only**: a stateless, batched, single-step native `step()`
selectable in place of `StubEngine`. The scheduler (§8) that *drives* it each tick, and
phase change (§7), are explicitly **out of scope** here.

## Decision: JNI, not Panama (supersedes DESIGN §2's wording)

DESIGN §2 specifies Panama (`java.lang.foreign`) and claims it is "stable on Java 21."
That premise is **false and was verified false**: on JDK 21 the FFM API is a *preview*
feature (JEP 442, third preview). It will not compile under `--release 21` without
`--enable-preview`, and preview-compiled classfiles (version `65.65535`) refuse to load
at runtime without the same flag (`UnsupportedClassVersionError: Preview features are
not enabled`). A vanilla Minecraft launcher runs `java` **without** that flag, and §3
requires the mod on **every client** — so a Panama build would fail to load for every
normal player and server.

**We use JNI instead.** It is fully stable on Java 21 (no preview, no flag, loads in any
launcher) and is also the *faster* choice for this workload:

- The per-step payload is large (per section: `matIx[4096]` + `mass[4096]` +
  `temp[4096]` + six 256-cell halo faces, batched over a player's section sphere). The
  conduction FLOPs dominate; per-call transition cost is negligible either way.
- The differentiator is array copies. JNI's `GetPrimitiveArrayCritical` hands the native
  kernel a **direct pointer into the Java heap array — zero copy** (it pins the array and
  briefly suspends GC relocation; safe because a step is bounded by §8's 1 s health
  budget). Panama **mandates** a copy: heap `MemorySegment.ofArray(...)` segments cannot
  be passed to a native downcall, so every array must be copied heap→off-heap and back on
  every call.

The conduction math is byte-identical regardless of binding. DESIGN §2 will be updated to
record this decision and its reason.

## Architecture

```
  Java (:core)                                C++ (ORGE-ENGINE submodule, additive)
  ────────────                                ─────────────────────────────────────
  OrgeEngine (iface, exists)                  orge_kernel.hpp  (new, header-only, SDL-free)
    ├─ StubEngine (exists, identity)            step_section_with_halo(...)  ← stateless
    └─ NativeEngine (new) ──orgeStep()──┐       (shared per-cell core w/ sim_engine.hpp)
  NativeLoader (new): extract+System.load │   orge_jni.cpp     (new) Java_…_orgeStep
  NeighborHalo (extended: temps+matIx)    └──> liborge.so      (new -shared target, SDL-free)
  EngineFactory (new): Native if lib loads, else Stub
  Gradle: pack src/main/resources/natives/<os>-<arch>/
```

### C++ side (ORGE-ENGINE submodule — additive; the SDL app stays intact)

1. **`orge_kernel.hpp`** — a new, header-only, SDL-free **stateless single-section
   stepper**. Given one section's `matIx[4096]`, `mass[4096]`, `T_in[4096]`; six halo
   faces each carrying neighbor temperatures **and** material indices; the material LUT;
   and `dt` → write `T_out[4096]`. It must replicate `simulate_section_16x16x16`
   **exactly**:
   - harmonic-mean conductivity `k_eff = 2·k₁·k₂/(k₁+k₂)`, and `k_eff = 0` if either
     `k ≤ 0` (insulator/void blocks flux);
   - `void` cells copy `T_in` through unchanged;
   - `Cth = max(1e-8, mass·heatCapacity)`; `T_out = T_in + (dt/Cth)·Σ k_eff·(T_n − T)`;
   - clamp `T_out` to `[0, 6000]` K;
   - neighbor order fixed `(+x,−x,+y,−y,+z,−z)` to preserve floating-point determinism.
   Interior neighbors come from the section's own 4096 cells; the six boundary faces come
   from the halo. An **absent** halo cell (sentinel) is treated as `void` → no flux,
   matching the engine's world-edge behavior.
   - Refactor `simulate_section_16x16x16` to delegate to the same per-cell core so the
     standalone app and the kernel share one source of truth (prevents drift).

2. **`orge_jni.cpp`** — JNI glue: `Java_net_rainbowcreation_orge_engine_NativeEngine_orgeStep(...)`.
   Header generated by `javac -h` from the `native` declaration (no jextract dependency).
   Uses `GetPrimitiveArrayCritical`/`ReleasePrimitiveArrayCritical` for zero-copy access,
   loops the batch invoking the kernel, writes results back into the output array(s), and
   reports per-step compute time (for `lastStepMillis`). Critical regions are scoped
   per-array and short.

3. **Build** — a `-fPIC -shared` `liborge.so` target that links **only** the kernel + JNI
   glue (no `main.cpp`, no `sim_server.hpp`, no `sim_render.hpp`, no SDL). Built locally
   here for `linux-x64`. The existing interactive SDL app remains a **separate** build
   target and is not modified beyond the shared-core refactor.

### Java side (`:core`, this repo)

4. **Extend `NeighborHalo`** to carry six material-index faces (`char[256]` each)
   alongside the existing six temperature faces. *Required*: boundary `k_eff` needs the
   neighbor's `thermalConductivity`, so the halo must carry "temps **and** material
   indices" (DESIGN §2's own words; the current record is temps-only — a real gap).
   `StubEngine` and existing tests are updated to the new shape.

5. **`NativeEngine implements OrgeEngine`** — flattens the batch into the contiguous
   primitive arrays the native side expects (geometry + temps + halos + LUT + dt), makes
   **one** `orgeStep` call, slices the flat result back into `List<float[]>` in task
   order, and sets `lastStepMillis` from the native timing. Declares
   `private static native void orgeStep(...)`.

6. **`NativeLoader`** — extracts the matching `natives/<os>-<arch>/liborge.{so,dll,dylib}`
   from resources to a temp dir and `System.load`s it (the old `SimServerManager`
   extraction trick, minus the subprocess). Detects os/arch, fails with a clear message if
   no matching library is bundled.

7. **`EngineFactory`** — returns a `NativeEngine` if the native library loads
   successfully, else falls back to `StubEngine`. Keeps `:core` runnable (and CI green) on
   platforms with no bundled `.so`.

8. **Gradle** — pack `src/main/resources/natives/<os>-<arch>/`. In-sandbox we build the
   linux-x64 `.so` locally and drop it in. The CI multi-platform artifact pull
   (`liborge-{os}-{arch}` from ORGE-ENGINE releases) is a **documented follow-up** — no
   network here.

### `:core` purity

`:core` must still **not** import `net.fabricmc.*` / `net.neoforged.*`. JNI loading is pure
JDK (`System.load`, `java.io`, `java.nio`) — no loader APIs — so `NativeEngine` /
`NativeLoader` / `EngineFactory` live in `:core` alongside the existing engine interface.

## Data flow (one step)

1. (Future §8) gathers `List<StepTask>` from the `SectionStore` for a player's sphere.
2. `NativeEngine.step(tasks, lut, dt)` flattens geometry, temps, halos (temps + matIx),
   and the LUT into primitive arrays.
3. One `orgeStep` JNI call: native pins the arrays (zero-copy), runs the kernel per
   section, writes `T_out`, records timing.
4. `NativeEngine` slices `T_out` into `List<float[]>` (task order) and returns it; (future
   §8) validates (§9) and writes back via `SectionStore.put`.

## Error handling

- **Library absent / wrong platform:** `NativeLoader` throws a clear diagnostic;
  `EngineFactory` catches and falls back to `StubEngine` (logged once).
- **Malformed batch (length mismatches, bad matIx range):** validated Java-side before
  the JNI call; throw `IllegalArgumentException` rather than risk a native out-of-bounds.
- **Native must not crash the JVM:** all indexing bounds-checked against the LUT size and
  the fixed 4096/256 lengths before dereference; absent-halo sentinel handled explicitly.

## Testing

**C++ (extends `tests/`, dependency-free, g++ -std=c++20):**
- Mirror the engine's invariant suite for the **stateless kernel**: void inert, uniform
  fixed-point, hot→cold (second law), energy conservation across section+halo, discrete
  maximum principle, insulator blocks flux, determinism.
- **Parity test (linchpin):** build a 2-section world, step it with the stateful `World`
  path (`compute_frame_to_backbuffers`), and step the same two sections via the stateless
  kernel feeding each section the other's boundary as its halo. Results must be
  **bit-identical**. This proves the kernel is a faithful refactor.

**Java (`:core:test`, JUnit 5 — native tests run here because g++ + JDK 21 are present):**
- With the real linux-x64 `.so` loaded: a **known-answer** conduction case (one hot cell
  beside a cold cell, one step) — `NativeEngine` output equals a hand-computed reference.
- `NativeEngine` ≡ `StubEngine` on a uniform field (both leave temps unchanged).
- Batch ordering: a multi-section batch returns results in task order.
- Marshalling round-trip: matIx/mass/temp/halo survive the flatten→native→slice path.
- **Native-absent path:** `EngineFactory` falls back to `StubEngine` (guarded so it also
  passes on a machine with no bundled library).

## Risks / notes

- `GetPrimitiveArrayCritical` pins arrays and disables GC relocation for its scope — keep
  critical regions short and per-array; a batch step is bounded by §8's 1 s budget.
- Cross-platform floating-point bit-identity is best-effort; the fixed neighbor-summation
  order keeps a single platform deterministic. Documented, not guaranteed across CPUs.
- Submodule pointer: commit C++ changes in `ORGE-ENGINE` first, then bump the gitlink in
  the parent `ORGE` repo (resolves the persistent `M ORGE-ENGINE`).
- `Material` carries the four constants the kernel needs (`heatCapacity`,
  `thermalConductivity`, `defaultMass`, `molarMass`); only the first three enter the
  conduction step. Validate non-negative/finite constants before the kernel divides by
  them (the §6-deferred guard — do it here since the engine is now the divider).
